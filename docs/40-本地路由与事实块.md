# 本地路由与事实块

> 本地路由 = 买家一句话 → **不调模型**判断「要取哪几块事实、谁先、缺了怎么说」。
> 事实块 = 每块事实的取数口径。两者分开，路由可测、取数可换。

---

## 一、分层

```
买家一句话
  ↓
server/fact-route.js      本地路由：asks / wanted（要哪几块、优先级）/ concern
  ↓
server/facts.js           事实包：按 wanted 取数 → 预算 → 编号
  ↓
模型（Pro）                只能用事实包 + used 引用
  ↓
server/judge.js           引用校验 / 数字有据 / 多意图覆盖
```

路由层只做判断，不读文件、不调网络、不生成话术。

---

## 二、路由表

### 2.1 问法 → 块

| ask | 块 | 说明 |
|---|---|---|
| price / stock / product / nego / spec | `product` | 需要已识别商品 |
| usage / recommend | `manual` | 说明书分节 |
| shipping_time / arrival_time / courier / freight / invoice / payment / return_policy / after_sale / privacy | `policy` | 知识库政策与通用说明 |
| shipping_status | `order` | 物流状态，必须有订单数据才答得上 |

### 2.2 优先级

`order(0) → product(1) → policy(2) → manual(3) → context(9)`

订单永远最前：问「我的这单」时，政策答不上「到哪了」。

### 2.3 订单信号（宁缺毋滥）

```
/我的(订单|快递|包裹)|这单|订单|单号|物流|到哪(了|儿)?|发了没|发货了吗|发出没|什么时候到|催(一下)?(发货|发|快递|物流)/
```

「查一下/催一下」单独出现**不算**订单——否则「查一下能不能便宜」会被当成问物流。
反例已进单测（R08）。

### 2.4 多意图

按标点拆子问题，最多取 3 个 ask；事实取并集。
路由出多个 ask 时，本地模板一律让位模型（`server/index.js` 的 `multiIntent`）。

## 三、事实块现状

| 块 | 来源 | 状态 |
|---|---|---|
| `order` | 会话右栏（未接） | ❌ 恒为 `missing: order`，只能给订单页口径 |
| `product` | `data/products.json` | ✅ 价格/库存/规格；`spec` 为空时用说明书「材质与规格」兜底 |
| `manual` | `data/manuals.json`（按 goodsId） | ✅ 商品卡标题能绑定；关切焦点过滤 |
| `policy` | `data/knowledge.json` | ✅ 检索命中；多意图补检索 |
| `context` | 商品标题 | ✅ 什么都没命中时的常驻层 |

## 四、为什么先做路由表

原来的判断散在 `facts.js` 的 `build()` 里：订单信号、字段选择、关切过滤、兜底常驻层混在一起。
加一块（订单/规格/物流）就要改 `build()`，也没法单独测「这句话到底该取哪几块」。

抽成表之后：

- 加一块 = 加一行 `ASK_BLOCK` + 一个取数器；
- 路由可以单测（R01~R09），不用起服务、不花钱；
- `facts.js` 只负责调度、预算、编号，职责单一。

## 五、兜底：扩召回（wide）

路由和事实块会一直补，但永远有没覆盖的问法。没覆盖时不能直接答“不知道”，
也不能让模型自由发挥，而是**分级扩召回**——把本店相关的相邻信息多给一点，同时守住预算和焦点。

### 5.1 三档

| mode | 什么时候 | 事实包 | 模型约束 |
|---|---|---|---|
| `normal` | 路由命中、块有内容 | 按块取，正常预算 | 按【事实】答 |
| `wide` | 路由没覆盖/块为空 | 放宽到相邻信息，预算 1200 | 多一句「信息可能不贴题，只取相关的」 |
| `empty` | 确实什么都没有 | 空包 + 缺失 | 只能给页面口径或反问 |

### 5.2 什么时候触发扩召回

| 触发 | 判断 |
|---|---|
| `no-core-facts` | 除了常驻层，一条事实都没有 |
| `uncovered:<ask>` | 问法对应的块没取到（如问规格但商品没有 spec） |
| `concern-gap` | 买家关切（中毒/凭证/地域）没有任何事实回应 |

多个条件同时满足时，trigger 用 `+` 拼起来（如 `no-core-facts+uncovered:spec`），便于排查。

### 5.3 扩召回补什么

| 来源 | 补什么 | 优先级 |
|---|---|---|
| 知识库 | 按整句再检索 top 3（不受 ask 标签过滤） | 5~7 |
| 说明书 | 没有分节命中时给摘要：每节标题 + 首句，最多 3 节 | 6~8 |
| 商品 | 连价格/库存都没取到时，至少给标题 + 价格/库存 | 5 |

**不补**：订单（没数据就是没有，补不出物流状态）。

### 5.4 三条硬约束

1. **只问物流且没订单 → 不扩召回**：`我的订单到哪了` 保持 `empty`，
   不拿「发货时间」这类政策凑数（实测：`mode=empty, items=[]`）。
   但「我的订单什么时候发货」会自动扩到「发货时间」——因为那句话真的问的是时效。
2. **有关切时只补回应关切的段落**：问「鹦鹉啃了会不会中毒」不会再补「适用对象」（ISS-007）。
3. **预算有上限**：正常 800 / 软 680；扩召回 1200 / 软 950、最多 12 条。
   超了按优先级丢，丢掉的记在 `budget.dropped`。

### 5.5 质检不放松

`wide` 只是给模型更多材料，**引用校验、数字有据、多意图覆盖照旧**。
模型引用了不存在的事实、报出事实里没有的数字，仍然兜底。

### 5.6 规格块（补记）

- 商品 `spec` 字段 → 事实包出「规格」事实；
- `spec` 为空但有说明书「材质与规格/尺寸」节 → 用说明书兜底，不算缺失；
- 两者都没有 → `missing: product/spec`，模型只能给「以商品页为准」。
- 有结构化规格时，本地「规格以商品页为准」会被让位给模型（`factsOverride`）。

### 5.7 怎么看到它

```bash
curl -s -X POST http://127.0.0.1:8787/api/facts/preview \
  -H 'Content-Type: application/json' \
  -d '{"buyerText":"能开发票吗","storeId":"real"}'
```

返回 `pack.route.mode / pack.route.widen / items / missing / budget`，不调模型、不扣点。

实测三条：

| 问句 | mode | 结果 |
|---|---|---|
| 能开发票吗（知识库有） | `wide` | 补到「发票」口径 |
| 多少钱（商品有） | `normal` | 只取价格 |
| 我的订单到哪了（无订单） | `empty` | 不硬凑政策 |

## 六、路由注册表（可增长）

静态路由表只能覆盖想到的问法。真实用户会说「发出来了没有呀」——静态表把它归成
「发货时间」，答「当天发货」，但买家问的是「我这一单发没发」。

注册表就是补这个：**短语 → 问法 → 需要的块 → 必须有的块**，可以测试中不断加。

### 6.1 存在哪

`data/fact-registry.json`，结构：

```json
{
  "version": 1,
  "entries": [
    {
      "id": "reg_shipped_or_not",
      "match": ["发货了吗", "发货了没", "发出了吗"],
      "ask": "shipping_status",
      "blocks": ["order"],
      "needs": ["order"],
      "note": "问这一单发没发，必须有订单数据",
      "source": "seed",
      "enabled": true
    }
  ]
}
```

- `blocks`：这句话要取哪几块；
- `needs`：没有这块数据就不能答，事实包会标 `missing`；
- `source`：`seed` 内置 / `learned` 测试中模型提议并采纳 / `manual` 手动加。

### 6.2 路由顺序

注册表**优先于**静态问法表：

1. 命中注册表 → 用它的 `ask` + `blocks`；
2. 没命中 → 走 `fact-route.js` 的静态 `ASK_BLOCK`；
3. 两者都要求块时合并去重，按 `order→product→policy→manual` 排。

注册表命中且 `needs` 缺失时（比如要订单但没有订单数据），
`server/index.js` 会强制走模型并带 `missing: order`，**不再让本地模板拿发货时效糊弄**。

### 6.3 测试闭环

```
测试会话 / 手动输入一句话
  → 本地路由没命中（mode=wide/empty）→ 记一条缺口（data/route-gaps.json）
  → 工作台「路由注册表」看到缺口
  → 点「让模型提议」→ 服务端 /v1/registry 判断需要哪些块（一次调用，不扣商家点数）
  → 人工确认/改字段 →「采纳并加入注册表」
  → 下次同一说法直接命中
```

缺口只在 `test: true` 的会话里记录，避免真实接待写满盘；同一句只累加次数。

### 6.4 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/facts/registry` | 条目 + 未处理缺口 |
| POST | `/api/facts/registry` | 新增/更新条目（`{entry}`） |
| POST | `/api/facts/registry/disable` | 停用（`{id}`） |
| POST | `/api/facts/registry/gaps/dismiss` | 忽略缺口（`{key}`） |
| POST | `/api/facts/registry/analyze` | 让模型提议（`{buyerText}`，一次调用，不扣点） |

### 6.5 实测证据（已确认事实）

- 「发货了吗」：注册表命中 `reg_shipped_or_not` → 事实包 `blocks=[order]`、`missing=order`，
  回答从「当天 16 点前发货」变成「单号会同步到订单，物流以订单页为准」，模型引用的是事实而不是猜。
- 模型提议「我买的东西发出来了没有呀」→ `shipping_status / order / needs order / 0.95`，
  采纳后 `preview` 显示命中 `learned` 条目，并标 `missing: order`。
- 缺口记录：「这个能寄到香港吗」→ `no-core-facts+concern-gap` 入 `route-gaps.json`。

### 6.6 边界

- 注册表只决定「取哪些事实」，**不改话术、不放松质检**；
- 采纳后可以停用，不删除历史（便于回滚）；
- 注册表命中不等于答对：没有数据时仍然标缺失、走兜底口径。
