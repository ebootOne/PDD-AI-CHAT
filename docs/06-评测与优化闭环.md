# 评测与优化闭环：让「答得准」变成可测量、可迭代的工程

> 角色：技术负责人（机制）＋ 产品经理（谁来做、做什么形式）
> 日期：2026-11-05
> 现状：`eval/cases.jsonl`（15 条样例）+ `scripts/eval.js`（打分器）已可运行，本轮把通过率从 **66.7% 提到 100%**。

---

## 一、先回答「谁来优化」：三层，职责不同

| 层 | 谁做 | 做什么 | 产出 | 能不能自动化 |
|---|---|---|---|---|
| **L1 基线** | 我们（厂商） | 通用评测集 + 品类知识包 + 打分器 | 每个版本的质量水位 | 半自动（人写用例，机器跑） |
| **L2 发现** | 工具（内置） | 从真实会话里找「答不上/被改/被转人工」的题，生成待办 | 每周知识缺口清单 | ✅ 全自动 |
| **L3 学习** | —— | 让模型自己改自己 | —— | ❌ **不做** |

**为什么不做 L3（自学习）**：
1. 不可审计——商用产品答错要能说清「为什么这么答」，自学习给不出；
2. 会漂移——今天学歪了，明天整店都歪；
3. 平台规则会变，模型自己学不会「新规则」，只有人能改。

**结论**：优化 = 人的判断 + 机器的发现。工具负责「把该改的地方找出来」，人负责「改成什么」。

## 二、评测集长什么样（已经落地的形式）

一行一条用例，JSONL，跟着代码走，能进版本库：

```json
{"id":"E001","intent":"logistics","difficulty":"easy","source":"种子店真实会话",
 "messages":[{"role":"buyer","text":"什么时候发货？"}],
 "expectDecision":"auto_send",
 "mustContain":["当天","16点"],
 "mustNotContain":["明天一定","保证"]}
```

四个关键字段：

| 字段 | 作用 |
|---|---|
| `messages` | 真实会话（可以多轮），不是造出来的假问题 |
| `expectDecision` | 该自动 / 该建议 / 该转人工——**决策错了，答得再好也是错** |
| `mustContain` | 必须说到的要点（发货时间、发芽率、退款条件） |
| `mustNotContain` | 绝对不能出现的词（承诺、极限词、站外联系方式） |

**为什么不用「标准答案精确匹配」**：客服话术有一百种正确说法，精确匹配会把对的判错，最后逼着团队去背答案而不是解决问题。所以只校验三件事：**决策对不对、要点在不在、红线碰没碰**。

## 三、打分器怎么跑（已实现）

```bash
node scripts/eval.js            # 跑全部用例
node scripts/eval.js my.jsonl   # 跑指定评测集
```

输出：总通过率、按意图分桶、失败明细（决策差异 / 缺哪个要点 / 碰了哪条红线）、`eval/last-report.json` 存档用于版本对比。

## 四、这一轮的真实闭环（66.7% → 100%）

这不是演示数据，是刚才真跑出来的：

| 用例 | 失败原因 | 归因 | 修法 |
|---|---|---|---|
| E003 催芽 | 意图判成 other，不给自动 | 意图词表缺「催芽/浸种」 | 补词表 |
| E008 发票 | 回复里没有「发票」二字 | 话术写法问题（写成「电子普票」） | 改知识文案 |
| E009 没拆封能退吗 | 直接转人工 | 知识关键词只有「退货/退款」，没有「退吗/拆封」 | 补关键词 |
| E010 江苏几天到 | 置信度 0.59 不达标 | 知识关键词没有「几天能到」这个说法 | 补关键词 |
| E015 宝贝还有吗 | 转人工 | 知识库没有「有货/库存」条目 | 补知识条目 |

**五条里有四条是「知识/词表」，一条是「话术」，零条是「模型不行」。**

这就是「比换模型有效十倍」的证据：**失败几乎都出在知识供给，不出在模型能力。**

## 五、闭环怎么转起来（工具内建的部分）

```
真实会话（脱敏）
   │
   ├─→ 自动入库 ──→ ① 未命中知识（无 KB 命中）
   │                ② 低置信度（< 0.7）
   │                ③ 被转人工（投诉/无依据）
   │                ④ 人工改写（AI 候选 ≠ 最终发送）★ 最有价值
   │
   └─→ 聚类成「知识缺口」→ 生成待办草稿 → 人确认 → 入库 → 跑回测 → 看通过率
```

### ④「人工改写」是免费标注，这是产品护城河

用户每改一次 AI 的话，就是一次免费的「标准答案」标注：

```
AI 候选：当天16点前付款的订单当天发出…
实际发送：亲，16点前拍下今天就能发走哈～
                      ↑ diff 就是学习信号
```

工具要做的是：**记录 diff + 归类 + 一键把改写采纳为知识**。用的人越多，知识库越准——这是竞争对手用模板库永远追不上的东西。

### 知识缺口发现器（v0.4 内置）

在客户端工作台加一个「待补知识」页，按出现频次排序：

| 问题（聚类后） | 出现次数 | 当前表现 | 一键补 |
|---|---|---|---|
| 「几天能到 XX」 | 128 | 置信度低 | 补关键词 |
| 「能便宜点吗」 | 96 | 无知识 | 新建话术 |
| 「发什么快递」 | 74 | 答非所问 | 修话术 |

> 这一页是给商家看的，不是给我们看的。**让商家自己把知识库养肥**，才可能规模化。

## 六、谁在什么时候做什么

| 周期 | 谁 | 动作 |
|---|---|---|
| 每次发版前 | 技术负责人 | 跑全量评测集，通过率低于基线不许发 |
| 每周 | 产品经理 | 看失败用例，决定补知识还是改话术 |
| 每周 | 工具（自动） | 输出「知识缺口清单」+「人工改写 top 20」 |
| 每月 | 产品经理 | 抽样 50 条真实会话做人工评审（机器打分测不出「像不像人」） |
| 每季度 | 技术负责人 | 重估模型选型与成本（模型降价很快，不要锁死） |

## 七、200 条评测集怎么攒（具体做法）

1. **取数**：导出最近 2 周真实会话（脱敏），按意图分层；
2. **分层**：每个意图 10–30 条，高频意图多放；
3. **写期望**：只写「必须说到的要点」和「绝对不能说」，不写标准答案；
4. **加难例**：投诉、索赔、站外引流、知识库没覆盖的问题各放几条；
5. **版本化**：`eval/cases-v1.jsonl` 之后只增不减，失败过的用例永久保留（回归防线）。

工作量：200 条约 2 人天（含脱敏与分层）。之后每周只增量维护 5–10 条。

## 九、结论

- **形式**：JSONL 用例 + 打分器 + 周报，已落地，不是 PPT；
- **谁来做**：我们定基线和品类包，工具负责发现缺口，商家负责确认；
- **不做**：模型自学习；
- **节奏**：每周回测，失败用例永久保留；
- **判断标准**：通过率不是越高越好，而是**「低置信度比例」和「人工改写率」持续下降**——那才说明知识真的覆盖了业务。
