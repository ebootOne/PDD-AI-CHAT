# 兜底策略：没有答案时，工具该做什么（已确认 / 已实现）

> 状态：**已按你的选择实现**（2026-11-05）。
> 背景：「没有答案 → 转人工」是错的，因为转人工不等于有人接。商家不在线时，买家就在等——这本身就在扣分。

## 已确认的决策

| 问题 | 你的选择 | 落地结果 |
|---|---|---|
| 兜底话术是否自动发 | **任何没答案的情况都发** | 不再判断在线状态，一律给回应 |
| 兜底几次 | 你提了「回复暂时无法回答 / 或调用模型」 | **不设硬上限**，按次数轮换话术；模型优先于兜底 |
| 投诉是否暂停 | **不暂停，继续兜底** | 投诉先安抚，之后转「暂时无法回答」，持续强告警 |
| 兜底计费 | （2026-11-05 调整） | **1 点**——只要给了可发送的回复就收费（含兜底/改写） |

## 一、先承认一个问题：现在的「转人工」是错的

拼多多考核 **3 分钟人工回复率**（08:00–23:00）。当前逻辑里，AI 答不上就直接不出声、进复核队列。

后果：

| 情况 | 结果 |
|---|---|
| 商家在线 | 没问题，人马上接手 |
| 商家不在（吃饭/外出/深夜/忙别的店） | **买家一直等 → 回复率掉 → 搜索权重掉 → 还可能差评** |

**所以「转人工」不是一个安全动作，它是一个把风险转嫁给商家的动作。**

---

## 二、新原则：AI 的职责不是「答对」，是「每条消息都有回应，且不制造新风险」

三个不变式：

1. **不能不说话**（除非商家明确要求静默）；
2. **不能编**（不知道就说不知道的委婉版）；
3. **不能承诺**（时间、赔付、价格、政策）。

---

## 三、决策矩阵（提案）

输入信号（都能从页面/配置拿到）：

| 信号 | 来源 |
|---|---|
| 知识置信度 / 是否打平 | 引擎 |
| 风险等级 | 投诉/索赔/站外/隐私 |
| **客服是否在线** | 页面「手机端客服在线接待中」文案 / 最近一次人工发送 < 5 分钟 / 手动开关 |
| 是否工作时段 | 08:00–23:00 |
| 本会话已兜底次数 | 会话状态 |
| 买家等待时长 | 最后一条买家消息时间 |

输出：

| # | 场景 | 动作 | 告警 |
|---|---|---|---|
| R1 | 有答案 | 正常回复 | 无 |
| R2 | 没答案 + **客服在线** | 不发兜底，只标记待办 | 普通 |
| R3 | 没答案 + **客服离线** + 工作时段 | **发兜底话术** | 强 |
| R4 | 没答案 + 客服离线 + 非工作时段 | 发兜底（夜间版） | 强 |
| R5 | 同一会话兜底已达 2 次 | 不再发，只告警 | 强 |
| R6 | 投诉 / 索赔 / 平台介入 | 发安抚兜底 + **暂停该会话自动回复** | 极强 |
| R7 | 兜底话术本身命中违禁词 | 不发，转人工 | 极强 |

## 四、兜底话术（默认三句，商家可改）

| 等级 | 场景 | 话术 | 禁忌 |
|---|---|---|---|
| L1 核实型 | 普通未知问题 | 「这个我需要确认一下，马上回您」 | 不说"几分钟" |
| L2 承接型 | 催发货/物流/售后流程 | 「收到，我这边帮您查一下，稍等」 | 不承诺时效、不报价 |
| L3 关怀型 | 投诉/索赔/情绪激烈 | 「非常抱歉，您的问题我记录下来了，马上安排人跟进」 | 不认责、不承诺赔付 |

**三句共同的禁忌**：不出现「赔」「退你钱」「保证」「X 分钟内」「最」「绝对」「微信」。

## 五、为什么这套对商家有利

| 商家损失 | 现状（只转人工） | 提案（兜底 + 告警） |
|---|---|---|
| 3 分钟回复率 | 掉 | 保住 |
| 买家流失 | 高 | 低（有人回应） |
| 错误承诺 | 无（AI 不说话） | 无（兜底话术不承诺） |
| 人工负担 | 事后补 | 事后补（一样） |

**代价**：买家可能觉得"在敷衍"。所以兜底次数必须限制（R5），且人一到就要接手。

## 六、配套要求

1. **在线状态检测**：优先读页面文案，其次看最近一次人工发送时间，最后给一个手动「我在/我不在」开关。
2. **兜底也要计入统计**：单独统计"兜底次数/兜底率"，兜底率高说明知识库覆盖不足。
3. **告警要能到人**：现在只有面板红点，商用版必须接微信/飞书/短信（否则人不在还是看不到）。
4. **审计**：每次兜底记录 触发原因 + 话术 + 是否有人接手。

## 七、需要你确认的五件事

1. **兜底话术允不允许自动发？**
   - 允许：保回复率，但买家可能觉得敷衍
   - 不允许：只内部提醒，商家不在时就是裸等
   - 我的建议：**允许**，但仅限 R3/R4/R6 三种场景

2. **同一会话最多兜底几次？** 我的建议：**2 次**，第 3 次只告警。

3. **"客服在线"怎么判定？** 我的建议：页面文案为主 + 最近 5 分钟有人工发言 + 手动开关兜底。

4. **投诉类要不要直接暂停该会话的自动回复？** 我的建议：**要**，人接手前不再自动发任何话。

5. **兜底话术给默认还是让商家自己写？** 我的建议：**给默认三句 + 可改**（商家不改就直接用）。

## 十一、兜底计费：已改为扣点（2026-11-05）

**结论：只要产出可发送的回复，就扣 1 点**，包括知识库兜底、质检驳回后改写的安抚话术。
只有「没有回复可发」（如未读到买家消息、点数不足直接拒绝）才不扣。

原方案是兜底 0 点，理由是不想让客户替我们的不足买单。用户决策改为收费，理由同样成立：
**回复本身就有价值（买家不用干等、商家不掉 3 分钟回复率），工具按交付收费。**

配套三条，避免变成"答不上还收钱"的坏体验：

1. **计费透明**：每条回复带 `costReason`（answer / rewrite / fallback / hold），日志可查；
2. **兜底率做健康指标**：兜底率高说明知识库没帮上忙，超阈值预警，而不是闷声收钱；
3. **点数不足即停**：不做赊账，余额为 0 直接拒绝并提示充值。

一句话：**钱要赚，但要让商家看得见自己为什么被扣。**

## 十二、预警推送（已实现）

![预警设置](../docs/screenshots/desktop-alerts.png)

### 触发条件

| 事件 | 默认阈值 |
|---|---|
| 连续无法回答 | 3 次（同一会话） |
| 投诉 / 索赔会话 | 每次（10 分钟冷却） |
| 点数不足 | 剩余 < 50 点 |

### 通道

| 类型 | 适用 | 说明 |
|---|---|---|
| 企业微信机器人 | 推荐 | 官方 webhook，5 分钟接入，稳定 |
| 飞书机器人 | 推荐 | 同上 |
| Server酱 | 推到个人微信 | 走服务号，需注册 |
| 通用 Webhook | OpenClaw / 自建网关 | POST JSON `{event, text}` |

**不做个人微信直连**（协议号）：封号风险高，一旦封了商家收不到告警，比不接更糟。

### 实测

本地起了一个 webhook 接收端，配置「连续 2 次兜底触发」：

```
第 1 次兜底 → 无推送
第 2 次兜底 → 推送成功
【客服预警】🔴 高
店铺：演示店
会话：test-conv
原因：连续 2 次无法回答
买家：你们老板叫什么名字
详情：建议补充知识库，否则会一直兜底
```
