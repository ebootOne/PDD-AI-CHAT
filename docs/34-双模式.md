# 双模式：普通（standard）与专业（pro）

> 这不是一个开关，是**两条产品线**。
> 以后改代码、写测试、记问题单，都必须说清"改的是哪条线"。

---

## 一、两条线是什么

| | **普通 standard** | **专业 pro** |
|---|---|---|
| 定位 | 走量、便宜、快 | 准确优先、长尾也能答 |
| 本地 | 主通道：命中即答 | 只保留高置信模板（≥0.85） |
| 模型 | 兜底：没答案/低置信才调 | 主通道：模板之外全部交模型 |
| 事实 | 知识库 + 商品字段 | 事实包（商品/说明书/订单/政策） |
| 延迟 | 毫秒级 | 1.5~2 秒 |
| 成本 | ≈0 | ≈¥0.0026/条 |
| 计费 | 1 点/条 | 模板命中 1 点；模型按档 1~3 点 |

---

## 二、代码分层（谁属于谁）

```
shared/   两条线共用
  judge.js      质检（依据/对题/承诺/立场）
  warm()        语气词
  concerns.js   安全/凭证/地域
  buffer.js     三级缓冲
  knowledge/manuals/products   取数层

standard 专属
  engine.js 里的本地候选路径（product / manual / rule + 置信度决策）

pro 专属
  facts.js      事实路由与事实包（待建）
  engine.js 的 pro 分支（低置信一律丢弃 → 模型）
```

**规则**：改 shared 影响两条线，必须两条线都回归。

---

## 三、怎么区分一次修改

每个改动/问题单都必须标注：

| 标记 | 含义 | 回归要求 |
|---|---|---|
| `standard` | 只影响普通模式 | 跑 `ENGINE=standard` |
| `pro` | 只影响专业模式 | 跑 `ENGINE=pro` |
| `both` | 共用层 | 两条都跑 |

问题单已加字段：

```bash
node scripts/issues.js add --engine pro --title "..." ...
node scripts/issues.js list     # 列表里会显示 (pro)
```

## 四、测试怎么跑

```bash
ENGINE=standard node scripts/logic-check.js
ENGINE=pro      node scripts/logic-check.js
node scripts/test-engine.js     # 引擎单测（默认 standard）
node scripts/eval.js            # 评测集
```

## 五、指标必须分开统计

| 指标 | 含义 |
|---|---|
| 本地命中率（standard） | 本地直接答出去的比例 |
| 模型调用率（pro） | 走模型的比例 |
| 兜底率 | 两条线分别算 |
| 单条成本 | 两条线分别算 |

混在一起算会得出错误结论：pro 的"本地命中率低"不是退步，是设计。

### 多意图为什么绕开本地模板

本地模板是「一条事实 → 一句回复」，它天然只能答一件事。
「能开发票吗，几天能到」命中发票条目后置信度 0.98，但「几天到」被整句丢掉了——
这不是置信度问题，是**表达能力**问题。所以 Pro 在事实包路由出多个 ask 时，
无论本地多确定都交给模型（`server/index.js` 的 `multiIntent`）。

普通版不适用这条：普通版的价值就是本地秒回，多意图留给后续迭代。
