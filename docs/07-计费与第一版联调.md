> 日期：2026-11-05
> 状态：本地模拟账本已实现（`server/quota.js`）；真实联调待商家账号就绪。

## 一、计价：对外「1 条回复 = 1 点」，对内「本地命中 = 毛利」

### 1.1 决定（按你说的改）

- **只要产出了可发送的回复，就扣 1 点**，不分本地还是模型；
- 转人工（没有产出回复）不扣；
- **本地命中不暴露给客户**——它是我们的成本优势，不是给客户的折扣。

### 1.2 为什么这样更赚（商人视角）

假设一条回复卖 0.02 元，一天 1000 条，本地命中率 80%：

| | 旧：本地命中免点 | 新：一律 1 点 |
|---|---|---|
| 收费条数 | 200 条 | 1000 条 |
| 收入 | 4 元/天 | **20 元/天** |
| 模型成本 | 200 × 0.004 = 0.8 元 | 0.8 元 |
| 毛利 | 3.2 元/天 | **19.2 元/天** |

同一套技术，同样的成本，毛利差 **6 倍**。

而且本地命中率越高，毛利越高——**这才是我们做厚知识库的真正理由：不是为了给客户省钱，是为了自己多赚。**

### 1.3 三条铁律

1. **计价规则必须一句话说清**：「1 条回复 1 点」。任何「这个免费那个收费」最后都会变成客诉和退款。
2. **买单的是「回复」，不是「模型调用」**。客户不关心我们用什么模型、跑在本地还是云端。
3. **点数必须预付费**。后付费 = 坏账，尤其是店群客户，跑路成本极低。

### 1.4 技术上怎么防止白嫖

本地命中也要扣点，就意味着**必须离线计量**，否则断网就能免费用。做法：

```
服务端签发额度凭证  { deviceId, quota: 500, exp, signature }
        ↓
客户端离线可用：每回复一条本地扣 1 点，写一条带递增序号的用量记录
        ↓
联网时批量上报 → 服务端核销 → 下发新凭证
```

- 模型调用仍然**必须联网**（Key 不下发），走服务端实时扣点；
- 每 7 天必须联网校验一次，否则停用；
- 单机日用量异常（比如一天 5 万条）触发风控。

**被破解的最坏情况**：本地知识库免费用。损失可控——破解版没有知识库更新、没有模型、没有售后，而且真正值钱的是持续更新的品类知识包。

### 1.5 定价策略：跟随竞品，低一档（2026-11-05 定）

用户策略：**竞品 5000 元 / 60 万条，我们卖 4000 元 / 60 万条，单价低 20%**，靠价差抢首批商家。

| | 竞品 | 我们（暂定） |
|---|---:|---:|
| 价格 | 5000 元 | **4000 元** |
| 条数 | 60 万 | 60 万 |
| 单价 | 0.0083 元/条 | **0.0067 元/条** |

不按成本定价，按竞品定价——成本只用来验证“这个价能不能撑住”：

- 实测单次模型成本约 0.0022 元（均值 584 tokens）
- 模型调用率 45% 时，单条成本约 0.001 元，毛利约 85%
- 即便 100% 调模型，毛利仍约 67%

**约束**：这个价格能打，前提是模型调用率 ≤ 50%、平均 tokens ≤ 700。两个指标一破，价差就变成亏损。

对外只讲“同样的 60 万条，少收 1000”，不讲成本、不讲毛利（见 AGENTS 第 12 条）。

### 1.5.1 旧定价框架（已作废，仅留档）

| 套餐 | 点数 | 价格 | 单价 | 适用 |
|---|---:|---:|---:|---|
| 尝鲜 | 500 | 19 元 | 0.038 | 一个店试一周 |
| 标准 | 5,000 | 149 元 | 0.030 | 单店一个月 |
| 专业 | 20,000 | 499 元 | 0.025 | 3–5 店 |
| 企业 | 100,000 | 1,999 元 | 0.020 | 10 店以上 |

单店日均 300 条 → 约 9,000 点/月 ≈ 225 元，对比一个客服 5,000–8,000 元/月，说服力足够。

### 1.6 隐私：能少传就少传

- 上传前脱敏：昵称打码、手机号/地址/订单号移除；
- 默认**不存会话原文**，服务端只存「用量 + 决策 + 是否命中知识」；
- 本地模式仍然保留，但需要定期联网校验额度。

## 二、"本地做不了，只能调模型"——这句话只对一半

| 能力 | 本地能做吗 | 说明 |
|---|---|---|
| 商品规格问答（品种/克数/播种期/发芽率） | ✅ 能 | 结构化字段 + 模板填空，覆盖头部问题 |
| 售后政策（退换/包邮/发票） | ✅ 能 | 固定话术 |
| 话术模板匹配 | ✅ 能 | 关键词 → 模板 |
| 多轮追问、上下文指代 | ❌ 弱 | 需要模型 |
| 长尾、口语化、没见过的问法 | ❌ 弱 | 需要模型 |
| 根据商品详情自动生成知识卡 | 🟡 半自动 | 抽取 + 人工确认 |

**所以不是二选一，是路由**：能本地答的本地答（不烧 token、快、稳），答不了的才调模型。对客户都按 1 点/条计价。

这也直接回答你的成本问题：**用的人越多，本地命中率越高，模型调用占比越低，毛利越好。**

## 三、第一版怎么落地（你注册店铺 → 上一个商品 → 手机提问 → 自动回复）

### 3.1 用哪个形态做第一次联调

**统一用桌面客户端联调。**

> 2026-11-06 起浏览器扩展已移除：页面适配逻辑在 `desktop/preload-cs.js` 里，客户端即唯一形态。

### 3.2 联调步骤（30 分钟）

**准备**
1. 启动服务：`node server/index.js`（已在跑：<http://127.0.0.1:8787>）
2. 启动客户端：`cd desktop && pnpm start`，切到真实店铺
3. 准备一个买家账号（手机 App 或另一台手机）

**主体**
4. 电脑登录 <https://mms.pinduoduo.com/chat-merchant/>，进入客服工作台
5. 看右侧是否出现「客服助手」面板
   - 出现 → 继续
   - 没出现 → 点页面任意聊天，再刷新；仍没有 → 点「诊断」，把 `data/diag-*.html` 发我
6. 手机上给这个店发一条：「什么时候发货」
7. 面板点「刷新」→ 确认「买家」栏显示的就是这句话
8. 点「生成回复」→ 看 3 条候选 + 依据
9. 点「填入输入框」→ 确认内容进了输入框 → **手动回车发送**（第一次一定手动，验证链路）
10. 打开面板右下角「自动」开关
11. 手机再发一条：「几天能到」
12. 观察：是否在 5–10 秒内自动发出（面板显示「可自动发送」）

**核对**
13. 客户端工作台 →「回复日志」应出现两条记录；
14. 手机端确认收到了第二条自动回复。

### 3.3 已知会失败的地方（提前说，免得白折腾）

| 现象 | 原因 | 处理 |
|---|---|---|
| 面板不出现 | 真实页 DOM 和模拟页不同 | 点「诊断」，我按真实结构改选择器 |
| 读到 0 条消息 | 会话列识别失败 | 同上 |
| 填入输入框后发送没反应 | 平台是受控组件，需要补发事件 | 现在已用原生 setter + input 事件；若仍失败，改用 Enter 键兜底 |
| 自动模式不触发 | 监听器没挂上 | 面板会显示「自动模式」但无反应 → 诊断 |
| 发出去的内容被平台拦截 | 命中平台违禁词 | 看平台提示，补进 `forbiddenOutput` |

**第一次联调大概率要改 2–3 处选择器，这是正常的，不是失败。**

### 3.4 商品知识怎么先建起来（你只有一件商品）

第一版不自动抓商品，先用客户端工作台的「知识库」手工建 5 条：

1. 发货时间（你店里的真实规则）
2. 到货时效
3. 商品规格（品种/克数/播种期/发芽率）
4. 售后政策（不发芽怎么办、退换）
5. 包邮/运费

> **数字必须是你的真实规则**，种子库里的「85%」「16 点」是模板，不能直接上线。

## 四、全天完整自动：可以，但三条保险我会写死

你选了全天完整自动。按你的决定做，但这三条不是可选项：

1. **夜间意图白名单**（23:00–08:00）：只答物流/规格，售后/投诉一律挂起并告警。
   —— 因为夜间回复**不计入考核**，收益为零，风险最高。
2. **熔断**：连续 3 条发送失败 / 出现验证码 / 识别不到消息 → 暂停该店并告警。
3. **投诉静默接管**：投诉、索赔、平台介入 → 只发安抚，不进自动队列，内部告警。

这三条都能在设置里关，但默认开。**关掉它们造成的赔付，合同里要写清楚由商家承担。**
