# 会话上下文与商品识别

> 触发：真实截图里，买家问「不出苗怎么办」，同时页面给出「当前用户来自 商品详情页 / 黑心乌菜种子…」。
> 工具要答对，必须先知道**这句话是在问哪个商品**，再知道**这个会话之前说过什么**。

---

## 一、截图中可用的三类信号

| 信号 | 截图里的样子 | 用途 | 可靠性 |
|---|---|---|---|
| 买家消息 | 「不出苗怎么办」 | 触发问题 | 高（气泡文本） |
| **商品卡** | 「当前用户来自 商品详情页」+ 商品名 + ¥1.28 | **确定在问哪个商品** | 高（平台自己给的） |
| 会话身份 | 顶部 `m***`、暂停接待状态 | 绑定上下文 | 中（昵称打码，需会话 id） |

**这张卡是整个工具的关键**：它替我们回答了「他在问哪款」。没有它，只能靠上一轮记忆或商品名匹配。

---

## 二、识别的落地顺序（技术）

```
① 页面商品卡（当前咨询商品）
      ↓ 没有
② 聊天流里的商品卡片消息
      ↓ 没有
③ 会话 URL / 参数里的 goodsId
      ↓ 没有
④ 商品名文本 → 匹配商品库（别名 + 品类）
      ↓ 没有
⑤ 上一轮记忆（lastProduct）
      ↓ 没有
⑥ 不猜：反问「您说的是哪一款？」
```

**每一步都要记录来源**（`product.source`），因为答错时要能说清是哪一步错了。

### 一个必须承认的事实

截图是**手机端拼多多商家版**；我们的工具嵌的是 **PC 商家后台客服页**。
两边的卡片结构不一定一样，**PC 端 DOM 至今没有用真实账号验证过**（红灯项）。

所以第一步不是写解析代码，是**拿真实账号抓一次页面结构**，确认商品卡长什么样。

## 三、上下文：存什么

```js
ConversationContext = {
  key,                 // storeId + buyerId（同一个人跨天进来也是他）
  buyer:  { id, name },
  product:{ goodsId, title, price, source },   // 当前焦点商品
  order:  { orderId, status },                 // 有就存
  slots:  { 地区, 数量, 时间 },                 // 从话里抽的实体
  turns:  [ { role, text, at, route } ],       // 最近 10 条
  done:   [ { type, at } ],                    // 已经答过/安抚过的主题
  counters:{ fallback, model, clarify },
  updatedAt
}
```

**只存这七样。** 存得越多，越容易过期、越难清理、越容易泄露。

## 四、上下文用在哪（产品需求）

### 4.1 六条硬需求（每条都有验收）

| # | 需求 | 验收标准 |
|---|---|---|
| C1 | **不问第二遍** | 已知道商品/地区/订单，后续回复不再追问同类信息 |
| C2 | **不复读** | 同一会话连续两轮的回复不得整段相同 |
| C3 | **记住承诺** | 上轮说过「会跟进」，下轮要接着这个事说，而不是重新开场（且只给态度承诺，不给流程承诺） |
| C4 | **焦点延续** | 「那要泡水吗」必须落在上一个商品上，不能换商品 |
| C5 | **商品切换** | 买家改问另一款时，焦点更新，旧商品信息不能混进来 |
| C6 | **交接可见** | 兜底/转人时，把「问的什么商品、之前说过什么」一并给到接手的人 |

### 4.2 三条禁止

- 不许把上下文当"记忆"乱用：**没有依据的推断不写进回复**；
- 不许把上一轮的错误答案继续沿用（错误也要记，但要标 `wrong: true`，下一轮不复用）；
- 不许无限堆历史：只给模型最近 10 条 + 结构化槽位，**不整段塞**。

## 五、生命周期（技术）

| 阶段 | 时长 | 存什么 |
|---|---|---|
| 活跃 | 最后一条消息后 **24 小时** | 完整上下文（turns ≤ 10 条） |
| 冷却 | 24 小时 ~ 7 天 | 去掉原文，只留 product / slots / done / 计数 |
| 归档 | 7 天 ~ 30 天 | 只留统计（条数、来源、兜底率） |
| 删除 | 30 天 | 全删（原文与买家标识） |

- 存储：本地 SQLite（每店一个库）或 JSON 分片；单会话上限 8KB；
- 并发：按 key 串行写，避免两个请求同时改写同一会话；
- 隐私：落盘前手机号/地址打码；提供「清空本会话」「导出」两个操作。

## 七、v1 实施顺序（建议）

1. **抓真实页面结构**（商品卡、消息、会话 id）——没有这个，后面都是猜；
2. `context.js`：内存 + 落盘，先只做 `product / slots / turns / done` 四个字段；
3. 接入三处：`router`（商品未知时反问）、`engine`（焦点延续）、`focus`（复读检测升级为"同一主题两轮"）；
4. 补 4 条验收用例（C1–C4 各一条），进评测集。

**不做**：跨会话的"客户画像"、购买历史、情绪画像——现在没有数据支撑，做了也是编。

## 八、上下文窗口策略（2026-11-07 更新）

| 层 | 内容 | 截断 |
|---|---|---|
| 客户端抓取 | 页面气泡，按左右分买家/客服，去重 | 最近 14 条 |
| 本地 → 模型 | 最近 12 条，每条 ≤300 字，手机号打码 | `slice(-12)` |
| 本地引擎 | 意图/检索只看最后一句；focus 用上一句客服回复 | — |
| 知识 | 最多 4 条，每条答案 ≤500 字 | — |

### 会话状态（新增）

每轮更新一份内存状态：

```
{ topic, answered[4], goods, turns, updatedAt }
```

- 传给模型：`【会话状态】当前话题：courier；已经答过：…`
- TTL 2 小时、最多 500 场，重启清空（暂不落盘）
- 会话 id：`storeId + hash(页面 URL)`，不再用买家昵称（避免同名串会话）

### 滚动摘要（2026-11-07 已做）

会话超过 12 条窗口后，把更早的部分**用规则压成一行**（不调模型、不额外花钱）：

```
早期问过：发货/快递/发票/议价；提到订单：1234****；提过售后/投诉
```

- 只提取：问过哪些话题、订单号（脱敏前 4 位）、是否提过售后/投诉；
- 挂在会话状态里，随 `【会话状态】` 一起给模型；
- 总长截 220 字，避免把 token 又吃回去。

实测 16 轮对话后，模型看到的是：

```
早期问过：发货/快递/发票/议价；当前话题：usage；正在聊：黄瓜种子…；已经答过：…
```

### 存储：按店铺分区 + 落盘（2026-11-07 已做）

```
data/sessions/<storeId>.json     每店一个文件
```

| 项 | 值 |
|---|---|
| 分区键 | `storeId` + `conversationId`（客户端 id = storeId + hash(页面 URL)） |
| 每店上限 | 300 场，超了淘汰最久未活跃 |
| 保留 | 24 小时 |
| 写入 | 防抖 2 秒 + 原子写（tmp → rename） |
| 隐私 | 只存本机；订单号只留前 4 位 |

实测：同一个 conversationId 在 `demo` 和 `other` 两个店互不影响；服务重启后摘要还在。

### 已知限制

1. 摘要靠规则关键词，不总结语义（不花钱的代价）；
2. 状态只存内存，重启即清；
3. 截断按“条数/字数”，不是按 token 预算；
4. 本地理解仍以最后一句为主，指代靠 focus 兜。

下一步优先级：状态落盘 > token 预算 > 摘要语义化（可选调小模型）。
