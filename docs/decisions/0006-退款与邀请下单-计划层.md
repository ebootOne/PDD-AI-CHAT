## 计划层规则

- 未发货 → 仅退款；
- 已签收 → 退货退款；
- 已发货/待签收 → 收到货不确定，需确认；
- 退款成功 → 不再发起；
- 商品 SKU 必须唯一匹配；无 SKU/多 SKU → 不自动发。

## 动作识别（服务端）

- 买家“我想退款/我要退货退款/申请售后” → action=refund；
- “怎么退款/退款多久” → 不动作，只回答；
- “邀请下单/发我商品/我要买” → action=invite；
- 退款缺收货状态/理由时 `canAuto=false`，先问或人工补；
- 动作只生成计划，不直接执行页面。

## 动作计划接渲染层

- 自动模式收到 `result.action=refund`：
  - 打开弹窗、选订单、填类型/收货/原因/金额；
  - `canAuto=true` 才提交；
  - 信息不全只填单并提示。
- 收到 `action=invite`：
  - 用当前订单商品+规格加入清单；
  - 不自动发送。

## 动作执行顺序

- 动作执行移到“自动回复发送完成”之后；
- 避免退款/邀请弹窗先打开，挡住 3 分钟必回；
- 回复优先，随后执行动作。

## 动作回复一致性

- 退款计划 canAuto=true 时，回复改为“这边帮您申请退货退款，请在卡片确认”，不再问“遇到什么问题”；
- 缺收货状态/理由时仍保留询问缓冲。

## 退款追问链路

- “帮我退下款，不想要了” → 退款动作；
- 缺收货状态时回“您收到货了吗”；
- 下一条“已经收到了” → 结合上一轮回退上下文，继续生成退货退款计划；
- 实测 canAuto=true，回复“这边帮您申请退货退款”。

## 防重复退款

- 当前会话已有 `waiting_buyer` 退款卡时，不自动再次提交；
- 记录 `action_skip`，提示“已有退款申请等待买家确认”。

## 邀请规格解析

- “邀请下单，要45mm、1头净蒜” → spec = “45mm 1头净蒜”；
- 规格从当前买家话里取，不沿用旧订单规格；
- 动作计划 canAuto 仍为 false，发送前需 SKU 精确匹配/确认。

## 退款原因映射平台枚举

- 空包 → 空包裹；
- 少发/漏发/少件 → 收到商品少件（含少配件）；
- 破损/污渍 → 商品破损或污渍；
- 错发/拍错 → 卖家发错货；
- 质量 → 质量问题；
- 不喜欢 → 不喜欢、效果不好；
- 不想要 → 不想要了；
- 缺货 / 发货慢。

## 模型动作 + 模板机制

- Pro 退款请求不再被本地退款缓冲提前拦截；
- 模型输出 `action`（kind/orderNo/refundType/received/reason/amount/needs）；
- 本地用 refund 模板校验：订单、类型、收货、原因枚举、金额默认订单实付；
- 信息完整 canAuto=true，回复“帮您申请退货退款”；
- 本地只在回复后执行，不再用关键词判断退款意图；
- 正则仅后端不可用时兜底。

## 模型能力目录

- 本地注册 refund/invite 模板，manifest 发给模型；
- 模型返回 action.kind；
- 本地模板校验槽位/枚举/金额；
- 退款 canAuto 完整才提交；
- 邀请 canAuto 由商品+规格决定，页面 SKU 唯一匹配才发送；
- 同规格邀请卡已存在时跳过。

## 本地完整命令 + 模型能力

- 模型 action 为主，正则仅兜底；

## 消费者自主售后卡

- 页面出现“消费者申请售后…去处理”，这是买家发起的售后，不是商家发起；

- 不生成退款动作。
