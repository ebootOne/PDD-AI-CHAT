# 上下文选择架构（重构目标）

> 不再按 intent/关键词决定“带哪些事实”。本地只提供候选池和硬约束，模型决定相关性、取舍和是否反问。

## 一、要解决的问题

现有结构：

```
买家话 → ask/intent → 本地决定带订单/商品/政策 → 本地选候选 → 模型润色
```

问题：

- 每出现一种组合（库存+订单、多订单+多商品、上下文指代）就加一个分支；
- 分支之间互相冲突，只能再加 guard；
- 本地做语义决策，模型只负责措辞，准确率上限被本地规则锁死。

## 二、目标结构

```
本地：候选事实池（带 ID）
  会话主题 / 当前商品 / 订单 / 商品目录 / 政策 / 说明书 / 档案
        ↓
模型：选择 used IDs + 回答 或 ask(哪一单/哪款)
        ↓
本地：校验 ID/门店/隐私/时效 → 执行发送或反问
        ↓
judge：只按 used 事实核验
```

## 三、不变量

1. **语义相关性只能由模型决定**：本地不得用 `ask`、关键词、`ORDER_SIGNAL` 决定带不带订单/商品。
2. **本地只做硬约束**：门店作用域、隐私、时效、违禁词、风险、3 分钟兜底。
3. **模型必须引用 ID**：`used` 只能来自候选池；不得编造订单号/商品/政策。
4. **一条买家消息只发一条**：反问也算回复；3 分钟内必发。
5. **删除一个旧分支，才能加一个新分支**：禁止只加判断不删旧判断。

## 四、代码调整

| 文件 | 现在 | 目标 |
|---|---|---|
| `server/fact-route.js` | ask/关键词决定事实块 | 只做硬约束/标签，不做语义取舍 |
| `server/facts.js` | 按路由决定是否带订单 | 构建候选事实池，全部带 ID |
| `server/engine.js` | 本地意图/多订单/多商品决策 | 只取候选；语义交模型 |
| `server/index.js` | 多处 lowLocal/multiEntity 分支 | 统一走模型 used/ask；保留 3 分钟兜底 |
| `server/judge.js` | 多订单/多商品/单位等 guard 叠加 | 按 used 事实核验；删除场景 guard |
| `pdd-cs-backend` | 只输出 candidates/used | 输出 used IDs + ask 动作 |
| 测试 | 单问法黄金集 | 增加“同一句话不同上下文”矩阵 |

## 五、迁移顺序

1. **候选池**：新增 `server/context.js`，把会话/订单/商品/政策统一成带 ID 的事实；
2. **模型选择**：Pro prompt 输出 `used`；模型选不齐就 `ask`；
3. **本地校验**：ID 必须存在、属于本店、无隐私；不合法丢弃；
4. **拆旧路由**：删除 `entitySensitive`、`ORDER_SIGNAL` 语义、多订单/多商品 guard；
5. **judge 改造**：只核验 used；
6. **上下文矩阵测试**：同一句“还有货吗”分别放在“其他品种 / 我买的 / 这个订单”三种上下文，验证选的 facts 不同。

## 六、验收

- 同一句话换上下文，选中的事实不同；
- 多订单/多商品/库存/物流不再靠新分支解决；
- 模型无依据时能反问或页面口径；
- 3 分钟内必有一条回复；
- 本地没有任何“按问法决定事实”的代码。

## 七、先不做

- 不再新增“stock 不带订单”“多订单问哪一单”这类场景规则；
- 不再用黄金集单条通过作为完成标准；
- 不在旧结构上继续加 guard。
