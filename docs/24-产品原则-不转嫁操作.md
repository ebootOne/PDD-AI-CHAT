# 产品原则：工具承担操作，不转嫁商家

> 来源：一次真实事故。联调时我给商家的步骤是「扫码登录 → 进入多多客服 → 停在会话上」，
> 其中后两步本来就是工具该做的事。**这不是流程没写清，是立场错了。**

---

## 一、归因（按 docs/16 五步）

| 字段 | 内容 |
|---|---|
| 场景 | 真实店铺联调，需要商家配合 |
| 我给的步骤 | 「扫码登录 → 进入多多客服 → 停在任意会话上」 |
| 失败类型 | **立场错**（把工具该承担的操作转嫁给商家）+ 流程设计错 |
| 还原诉求 | 商家要的是「打开就能用」，不是「按说明书操作」 |
| 缺失思维 | **操作归属**（operation ownership）：每一步先判断“这是操作还是决策” |
| 思维定义 | 输入=一个步骤 → 判断=商家必须亲自做的只有**身份验证**和**决策**，其余都是工具的事 → 输出=工具做，失败时工具自救，不自救才升级给人 |
| 改哪一层 | 产品流程 + AGENTS 规则 + 联调协议 |
| 验收 | 首次使用，商家动作只剩「扫码 1 次」；联调协议里不得出现“请你去点 XX” |

---

## 二、判据：操作 vs 决策

| 事项 | 谁做 | 理由 |
|---|---|---|
| 打开登录页、跳转 | **工具** | 纯导航 |
| 扫码 / 短信 / 人脸 | 商家 | 身份验证，无法代办 |
| 登录后进入「多多客服」 | **工具** | 纯导航 |
| 选会话、轮询未读、切店 | **工具** | 纯操作 |
| 找商品、找订单、读商品卡 | **工具** | 纯读取 |
| 生成候选、填输入框 | **工具** | 纯操作 |
| 发不发、改哪句 | 商家 | 决策（也是责任） |
| 授权、资质、付费 | 商家 | 责任 |

**一条判据**：这件事做错了，谁承担后果？
- 工具承担 → 工具做；
- 商家承担 → 商家决定，但**操作仍由工具执行**（比如“发不发”由商家决定，“发送”这个动作由工具做）。

---

## 三、三条推论

1. **联调协议里不允许出现“请你去点 XX”**，除非那一步是身份验证。
   正确写法：「你只需要扫码，剩下我来」。
2. **工具失败要自救**：读不到、跳不过、找不到 → 工具自己重试 / 诊断 / 降级，不把排查丢给商家。
3. **首次使用的动作预算 = 1 次扫码**。超过这个数，就是产品设计问题，不是用户问题。

---

## 四、变体与反例（验收用）

**同类变体 ×3**（都应该被判为“工具该做”）：
1. “麻烦你先切换到多多客服页面” → 应改为工具自动跳转；
2. “请在左侧点开一个有商品卡的会话” → 应改为工具自动定位最近会话；
3. “请把商品 ID 复制给我” → 应改为工具从页面商品卡读取。

**反例 ×1**（不该被工具代做）：
- “请把验证码填一下” → 属于身份验证，工具不能代办，只能就地提示并等待。
