# 商品同步：什么时候同步、怎么更新、怎么保证不乱

> 商品库是回复的「事实来源」：有没有货、多少钱、哪一款。
> 它错一次，商家就答错一次。所以同步不是"抓一下"，是要**严格处理**的功能。

---

## 一、结论先行

| 问题 | 结论 | 理由 |
|---|---|---|
| 登录时同步吗 | **登录后台自动同步，不阻塞使用** | 符合规则 16：工具做事，商家不操作 |
| 更新方式 | **自动为主（登录 + 定时 + 进客服页），手动兜底** | 商品价格/库存天天变，靠商家点按钮必然过期 |
| 让商家选"是否自动"吗 | **不选**，默认自动；只给「暂停同步」开关 | 把"要不要保持准确"交给商家，等于把责任丢给他 |
| 同步失败了怎么办 | **绝不覆盖旧数据**，标记过期并降级回答 | 宁可说"以页面为准"，不能说错价 |

---

## 二、触发时机（三档）

| 时机 | 频率 | 说明 |
|---|---|---|
| **登录成功后** | 每次 | 后台跑，先让商家能回消息，商品库边同步边补 |
| **进入客服页** | 每次进入 | 距离上次成功 > 30 分钟才真的跑 |
| **定时** | 每 30 分钟 | 只在工具运行且空闲时跑，避免抢资源 |
| 手动 | 随时 | 设置里「立即同步」，给不放心的商家 |

**不做**：每次回复前同步（太慢、会触发风控）。

---

## 三、严格处理：五条铁律

1. **只读不写**：只从商家后台读商品，绝不改商品、不改价格。
2. **全量成功才替换**：抓到一半失败 → 保留旧数据，标记 `stale`，不半新半旧。
3. **异常不覆盖**：新抓条数 < 旧库 50% → 视为抓取不完整，**拒绝覆盖**并告警。
4. **带时间戳**：每个商品记 `syncedAt`；价格/库存超过 24 小时 → 不再报具体数字，改说"以页面为准"。
5. **可回滚**：每次同步保留上一版快照，出问题一键回退。

---

## 四、同步什么、不同步什么

| 同步 | 不同步 |
|---|---|
| 商品 ID、标题、价格、库存、状态（在售/下架） | 买家信息、订单明细 |
| 规格、图片、更新时间 | 聊天记录 |
| 说明书（商家自己写的，独立维护） | 竞品数据 |

**下架不删除**：标记 `inactive`，保留历史（说明书还挂在上面）。

Product = {
  goodsId, title, price, stock, status,   // on_sale / off_shelf

SyncMeta = {
  lastSuccessAt, lastAttemptAt, count,

  result,                                   // ok / partial / failed
  prevSnapshot                            // 回滚用

## 六、失败与降级（用户能看到什么）

| 状态 | 商家端显示 | 回复行为 |
|---|---|---|
| 从未同步 | 「商品库待同步」 | 只答店铺政策，不答"有没有/多少钱" |
| 同步中 | 「同步中…」 | 同上，不阻塞 |
| 成功 | 「商品 128 件 · 10:32 更新」 | 正常 |
| 部分失败 | 「部分商品未同步，已保留上次数据」 | 用旧数据，但标 stale |
| 全失败 | 「同步失败，点此重试」 | 用旧数据；超过 24h 则降级为"以页面为准" |

**原则：同步出问题，不打扰商家做生意；但也不能让旧数据冒充新数据。**

## 七、验收标准（PM）

| # | 标准 | 怎么验 |
|---|---|---|
| S1 | 登录后 0 操作，5 分钟内商品库可用 | 登录 → 等 5 分钟 → 看条目数 |
| S2 | 同步不阻塞回复 | 同步中仍能生成回复 |
| S3 | 下架商品 30 分钟内不再被推荐 | 下架一个 → 30 分钟后问"有 X 吗" |
| S4 | 价格过期不报数字 | 改 24h 前的时间戳 → 问价格 → 应答"以页面为准" |
| S5 | 抓取不完整不覆盖 | 人为让抓取少一半 → 旧数据仍在 |
| S6 | 一次同步可回滚 | 触发回滚 → 恢复上一版 |

## 八、技术实现（下一步）

1. 从商家后台「商品列表」页抓（同一登录态，免二次登录）；
2. 分页/滚动到底，记录条数与耗时；
3. upsert 到 `products.json`，写 `SyncMeta`；
4. 引擎读取时过滤 `status=on_sale` + `syncedAt` 在阈值内。

**风险**：商品列表页 DOM 未取证（只取证了客服页）。需要先抓一次结构再写解析。

## 九、和规则 16 的关系

「让商家手动录入商品」违反规则 16（工具承担操作）。
所以默认自动；商家唯一的动作是「暂停」或「立即同步」——都是控制权，不是劳动。

## 十、同步策略（2026-11-09 补）

> 教训：商品数据停在 2 天前，`syncMeta` 却显示"同步成功"——因为店铺 id 变了（real → smw8rjgmx），
> 写进去的条目没落到当前店铺。**报成功不等于写成功。**

| 机制 | 做什么 |
|---|---|
| **写后校验** | 同步完立刻回读 `/api/products?storeId=`，条数为 0 或 `syncedAt` 不是刚刚 → 判失败 |
| **新鲜度巡检** | 每 10 分钟检查一次；`lastSuccessAt` 超过 30 分钟 → 自动补同步 |
| **状态可见** | 状态栏显示：同步中 / 已同步 N 件 / 失败 / 未校验通过 / 已过期 |
| **回答层兜底** | 商品 `syncedAt` 超过 2 小时 → 引擎不再用它报价报库存，改口径"以商品页为准" |

**原则：数据有时效，代码要自己知道它过期了，而不是等人发现。**

测试侧同步调整：`logic-check` 启动时自动挑「数据最新」的店铺，避免拿过期数据自证逻辑正确。
