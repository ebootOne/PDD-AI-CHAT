# 敏感词：词从哪来，闸门放哪

> 结论先说：**平台没有公开可下载的「敏感词表」，只能按规则场景自建分层词表；拦截必须放在本地后置，前置约束只用来降低概率。**

---

## 一、调研结论（证据分级）

### 已确认事实

- 拼多多有官方**规则中心**（商家后台 `mms.pinduoduo.com/other/rule?id=...`），例如 [规则中心 id=181](https://mms.pinduoduo.com/other/rule?id=181#1)、[id=1449](https://mms.pinduoduo.com/other/rule?listId=24&id=1449#1)。
- 这些页面需要商家登录，且是 JS 应用——抓取只能拿到标题，**没有公开正文、也没有可下载的词表文件**。
- 平台判违规是**按场景**：虚假宣传、站外导流、服务态度、极限词、功效宣称，而不是逐词清单。

### 第三方经验（暂定理解，不可当平台标准）

行业文章把拼多多高危词归成几类：绝对系、全网系、终极系、唯一系、第一系，以及导流（微信/电话）、赔付承诺、夸大促销。参见 [客服违禁词整理](https://www.mmker.cn/article/13081.html)、[禁用词设置实操](https://insight.xiaoduoai.com/e-commerce-information/pinduoduo-information/banned-words-pinduoduo-set-customer-service.html)。

这些是经验总结，**不同类目、不同时期口径会变**，只能作为初始词表，不能写成"平台规定"。

### 因此

1. 词表要**可热更新**（平台改口径时不用发版）；
2. 每条词要带**来源**（平台规则 / 广告法 / 店铺自定义）和**级别**；
3. 不能只靠词表——词表是兜底，规则场景（导流、赔付、绝对化）才是骨架。

## 二、闸门放哪：前置 vs 后置

| | 前置（喂给服务端模型） | 后置（本地出厂校验） |
|---|---|---|
| 作用 | 降低生成概率 | 保证结果 |
| 可靠性 | 模型可能不遵守、可能换供应商 | 只有这里能保证"每个字都过检" |
| 延迟/成本 | 无额外 | 本地毫秒级 |
| 隐私 | 词表要传给服务端 | 不出本机 |

**结论：两道都要，但真正的闸门必须在本地后置。**

理由很直接：服务端返回什么，客户端控制不了；只要闸门在服务端，换模型、换供应商、服务端被改，闸门就失效。商家电脑上的最后一道扫描，才是可承诺的那道。

前置只做一件事：把"禁止出现的表达"拼进服务端请求的约束里，让模型少生成。**它是概率优化，不是合规保证。**

## 三、现在的实现

```
服务端返回候选 ──► 本地 sensitive.check ──► block: 丢弃该条
                                          └► warn : 保留 + 记录
本地知识库候选 ──► engine.screenOutput（同一套 check）
```

| 文件 | 作用 |
|---|---|
| `data/sensitive.json` | 词表（可热更新），带 level / reason / source |
| `server/sensitive.js` | 加载词表、分层校验；文件缺失时用内置默认词表 |
| `server/engine.js` `screenOutput` | 本地候选过闸，block 丢弃、warn 记录 |
| `server/index.js` | **服务端返回的候选同样过闸**（此前是漏洞：服务端候选没走本地违禁词） |
| `scripts/test-sensitive.js` | 3 条该拦 + 1 条反例 |

### 三条设计取舍

1. **不拦裸词「微信」**：知识库的支付方式回答里有「支持微信、支付宝」，拦了就误杀。要拦的是「加微信」这类导流说法。
2. **block 丢整条候选**，不是打码：打完码的话术发出去仍然违规，且显得心虚。
3. **warn 保留但记录**：促销词（秒杀/抢购）不必然违规，拦了会丢转化；记录后让商家自己判断。

## 四、前置约束怎么发（待接）

服务端请求里加一个 `constraints` 字段：

```json
{
  "constraints": {
    "forbidden": ["加微信", "保证", "100%", "全网最低"],
    "rules": ["不得承诺赔付", "不得引导站外", "不得替平台做退款决定"]
  }
}
```

服务端把它拼进 system prompt。**但本地后置校验不因此省掉。**

## 五、还没确认的

| 事项 | 状态 |
|---|---|
| 平台规则原文（需商家登录人工核对） | 待确认，不能替商家承诺"这样发一定不违规" |
| 类目差异（农资 / 食品 / 化妆品词表不同） | 待定，当前是种子/农资口径 |
| 词表是否下发给服务端、如何保持同步 | 待定 |
| 命中率与误杀率 | 需要在真实会话里统计，目前只有机制测试 |
