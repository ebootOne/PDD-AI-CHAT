# 事实包协议（Pro）

> 一句话：本地只负责「取事实」，模型只负责「组织语言 + 引用编号」。
> 本文是 `server/facts.js` 与 `pdd-cs-backend` 之间的契约，改字段两边一起改。

---

## 一、为什么要有这一层

普通版是「本地命中就答」；Pro 是「本地只保留高置信模板，其余交模型」。
模型答错通常不是措辞问题，是**知道得不对**：

- 该拿的事实没拿（问「我的这单」却只给了店铺政策）；
- 拿得太多（把整段说明书和无关知识塞进去，模型抓错重点）；
- 没来源标记（模型把「通用建议」写成「本店承诺」）。

事实包把「取数」和「措辞」拆开：路由决定拿哪几块，每块只取必要字段，
每条事实带 id，模型输出 `used`，质检按 id 验真。

## 二、客户端 → 服务端

```json
{
  "facts": {
    "version": 1,
    "route": {
      "blocks": ["product", "manual", "policy"],
      "asks": ["price", "usage"],
      "orderAsked": false,
      "reasons": ["问到价格/库存/商品", "问到这款的用法/规格"]
    },
    "items": [
      { "id": "F1", "block": "product", "label": "价格", "text": "白萝卜种子：9.9 元起（最高 12 元）" },
      { "id": "F2", "block": "manual", "label": "要不要泡水", "text": "要泡水的。播前用 30℃ 温水浸种 4~6 小时……" }
    ],
    "missing": [{ "block": "order", "reason": "no-order-data" }],
    "budget": { "limit": 800, "soft": 680, "tokens": 132, "dropped": [] }
  }
}
```

### 块（blocks）

| block | 取数来源 | 什么时候取 |
|---|---|---|
| `order` | 会话右栏订单（**未接入**） | 出现「我的 / 这单 / 订单 / 单号 / 物流 / 到哪」 |
| `product` | `data/products.json` | 问到价格 / 库存 / 规格，且商品已识别 |
| `manual` | `data/manuals.json`（按 goodsId） | 说明书分节命中 |
| `policy` | `data/knowledge.json` | 知识检索命中，或多意图补检索 |
| `general` | 知识库里的通用说明 | 命中但没有店铺承诺属性 |
| `context` | 商品卡标题 | 什么都没命中时的常驻层 |

### 缺失（missing）

`missing` 是**给模型的禁令**，不是内部日志：列出的块，模型只能给
「以订单页/商品页显示为准」这类口径，不许编状态、时间、金额。

| reason | 含义 |
|---|---|
| `no-order-data` | 买家问到这一单，但客户端还没接订单面板 |
| `no-spec-field` | 商品目录没有规格字段 |
| `no-evidence` | 买家关切（安全/凭证/地域）没有事实能回应 |
| `no-facts` | 整包为空 |

### 预算

- 硬上限 800 tokens，实际目标 680（留估算误差余量）；
- 单条事实 ≤190 字，超长按句末截断；
- 最多 8 条；超了就按优先级丢，丢掉的记在 `budget.dropped`（原因 `budget` / `max-items`）；
- token 是估算（中文 0.7/字、英文 1.3/词），不是分词器精确值——**宁可多算，不许顶穿**。

### 隐私

- 只读白名单字段，收件人/电话/地址永不进包；
- 订单只允许状态、付款/发货时间、快递公司、运单**尾号**；
- 客户端 `facts.scrub()` 洗一遍，`backend.maskFacts()` 再洗一遍（服务端不可信）。

## 三、服务端渲染与输出

带 `facts` 的请求走 `SYSTEM_PRO`，把事实渲染成：

```
【事实】
[F1] 价格：白萝卜种子：9.9 元起（最高 12 元）
[F2] 要不要泡水：要泡水的。播前用 30℃ 温水浸种 4~6 小时……
【缺失】order（只给页面口径，不许编）
```

模型输出增加 `used`：

```json
{ "used": ["F1"], "candidates": [...], "need_human": false }
```

服务端只做长度/条数裁剪与去重，**不替模型判断引用对不对**——那是客户端质检的事
（服务端只负责记账与转发，验真必须在客户端手里）。

不带 `facts` 的请求完全走旧路径（`SYSTEM` + 【资料】），普通版不受影响。

## 四、客户端质检（judge.js）

`facts` 存在时，在「依据」检查之后追加三条：

| 检查 | 判据 | 不过时 |
|---|---|---|
| 引用存在 | `used` 里每个 id 都在包内 | 兜底（按无依据） |
| 数字有据 | 店铺事实类回答里的数字必须出现在事实原文 | 兜底（按编造） |
| 多意图覆盖 | 问了几类，回复里要有对应信号；只答一半 | 兜底 |

通用常识类（usage/种植）不做数字校验：`0.5 厘米` 这种不是店铺承诺。

---

## 五、路由与多意图

1. 有「我的/这单」→ 强制带 `order` 块（没有数据就进 `missing`）；
2. 退款/售后 → 订单优先于政策；
3. 商品名/商品卡 → 商品块 + 说明书节；
4. 多意图 → 按标点拆子问题，事实取并集，**本地模板一律让位给模型**；
5. 都没命中 → 只给常驻层，模型只能问/兜底。

第 4 条是 ISS-008 的机制修复：不是给某句话加特判，而是「一句话问两件事时，
单条模板不可能答全」这个判断本身。
