# 桌面客户端 · 多店内嵌 · 全店巡场 —— 技术方案与风险

> 角色：技术负责人（可行性）＋ 产品经理（形态与商业判断）
> 日期：2026-11-05
> 前提：工具版（本地安装、卖授权），Windows + Mac，真实登录商家后台，多店铺，全店巡场自动回复。

---

## 一、竞品形态拆解：左边店铺列表 + 右边内嵌浏览器切换

你看到的那个形态，实现方式基本只有一种：

**每个店铺 = 一个独立的浏览器会话分区（cookie jar），页面常驻内存，切换只是「显示/隐藏」，不是「重新加载」。**

所以你会看到：点左边「磐叶」，右边瞬间就是那个店的客服页，甚至停在刚才的会话上——因为它从来没被销毁过。

这在这套技术栈里是标准做法，可行。

---

## 二、实现方案：Electron + 每店一个持久分区

### 2.1 结构

```
┌──────────────────── Electron 主窗口 ────────────────────┐
│ 左侧：店铺列表（React）   │ 右侧：内容区（多个 WebContentsView 叠放）│
│  · 磐叶  未读 3          │  ┌──────────────────────────────┐ │
│  · 四季  未读 0          │  │ 店铺A 的客服页（persist:shop-A）│ │
│  · 乡野  正常            │  └──────────────────────────────┘ │
│  · 优种  掉线            │  （其余店铺的 View 不可见但仍在跑）  │
└─────────────────────────────────────────────────────────┘
```

### 2.2 关键实现点

```js
// 1) 每个店一个持久分区：登录态互不干扰，重启后还在
const sess = session.fromPartition(`persist:shop-${shopId}`)

// 2) 每个店一个常驻 View（Electron 30+ 的 WebContentsView）
const view = new WebContentsView({ webPreferences: { session: sess, preload } })
win.contentView.addChildView(view)

// 3) 切换店铺 = 改可见性，不销毁、不重新加载
view.setVisible(false)         // 或把 bounds 移出可视区
view.setVisible(true)
```

**为什么不用「同一个 view 切换 cookie」**：那样每次切店都要重新加载页面、重新登录、丢掉滚动位置和未读状态，体验和竞品差一个档次，而且频繁切 cookie 更容易触发风控。

### 2.3 注入方式：用 preload，不用扩展

Electron 里我们**不需要浏览器扩展**——`preload` 脚本可以直接在页面上下文里读写 DOM，能力更强、不受商店审核、更新随应用走。

> 这意味着 v0.1 写的 `content.js`（会话识别、填输入框、点发送）可以几乎原样搬进 preload。之前的投入不浪费。

### 2.4 内存与降级

| 店铺数 | 常驻内存估算 | 处理 |
|---|---|---|
| 1–5 店 | 1–2 GB | 全部常驻 |
| 6–12 店 | 2–4 GB | 常驻热点店，冷店 30 分钟无活动后 `webContents.close()`，切回时懒加载 |
| 12 店以上 | 4 GB+ | 必须做「分组轮值」：同一时刻只有一组店在线巡场 |

这是产品必须写进配置的硬约束，不能假装无限。

## 三、全店巡场：技术上能做，但坑在「批量事故」

### 3.1 巡场状态机（每店一条独立状态机，串行执行）

```
空闲
 └─(每 5~10s 轮询会话列表)
      ├─ 无未读 → 回到空闲
      └─ 有未读 → 取最早/最高优先级的一条
            ├─ 点击会话 → 等消息渲染完（最多 3s）
            ├─ 读最后 N 条 → 判断是否买家最后发言
            ├─ 生成回复 → 校验（违禁词/置信度/风险）
            ├─ 填入 → 随机 2~5s → 点发送 → 回读确认已发出
            └─ 下一条
```

### 3.2 必须有的熔断（这是产品存活的关键）

| 触发条件 | 动作 |
|---|---|
| 连续 3 条发送失败 | 暂停该店，顶部告警 |
| 识别到验证码/滑块 | 立刻暂停该店，弹窗让人工过 |
| 会话被扣「已转人工」或出现投诉关键词 | 停止自动回复该会话，转「静默接管」 |
| 单店 1 小时内自动回复 > N 条（如 120） | 降速或暂停，防机器速度暴露 |
| 置信度低的比例 > 30% | 全局告警：知识库覆盖不足 |
| 页面结构连续 3 次识别不到消息 | 暂停 + 上报诊断快照 |

**没有熔断的全自动 = 一次页面改版就能在半小时内把 8 个店答崩。**

### 3.3 「人味」节奏

平台看不到你的代码，但看得到行为：切会话间隔、打字速度、回复时长分布。机器速度是最大的破绽。

- 会话切换间隔 3–8s 随机；
- 发送前 2–5s 随机；
- 单店并发 1（绝不并发多会话）；
- 深夜降速或只接不答。

## 四、最大的技术风险：指纹与验证

Electron 的内嵌 Chromium 和真实 Chrome 有差异（UA、`navigator.webdriver`、部分 API），拼多多的风控可能会：

- 频繁弹滑块；
- 判定异地/异常设备，强制重新登录；
- 对自动化行为限流。

**这是本项目唯一「做之前不知道能不能过」的环节。** 处理办法：

1. 启动参数对齐真实 Chrome（UA、语言、时区、`--disable-blink-features=AutomationControlled`）；
2. 不做任何 `navigator.webdriver` 伪造之外的激进对抗（不伪造硬件指纹，那是给自己埋雷）；
3. **第一周就做「体检」**：新装 Electron 壳，登录一个店，正常人工用 3 天，统计弹验证次数。如果一天弹 5 次，这条路就要重新评估。

> 备选方案：Electron 只做 UI 与调度，真实浏览器用本机 Chrome（`--remote-debugging-port` + 独立 Profile）由 CDP 驱动。指纹 100% 真实，代价是「内嵌感」没了，窗口是独立的。这是指纹过不去时的退路。

## 五、一键评论（感谢评价）

独立模块，挂在同一个 Electron 里，打开「评价管理」页做 DOM 自动化。

- 技术难度：**低**（非实时、非对话、可批量、失败可重试）；
- 商业价值：**高感知、低风险**，是很好的「第二个卖点」；
- 红线：**不能出现「好评返现」「给好评才发货」**，感谢话术必须纯感谢、不带利益诱导。

建议放到 v1.5，等巡场稳定后再做。

## 六、关于「不做转人工」：我建议改成「静默接管」

竞品的做法是：用户说「转人工」，AI 回「我就是」。这在体验上确实顺，但有两个问题：

1. **合规与信任**：不能否认用户对「人工」的诉求。更好的话术是「我就是客服，您的问题我直接给您处理」——不撒谎，也不推诿。
2. **风险**：投诉、索赔、平台介入这类会话，AI 越答越糟。竞品敢这么做，是因为它把风险转嫁给了商家。

**我的方案：不打断买家，但内部接管。**

| 场景 | 对买家 | 对商家 |
|---|---|---|
| 普通咨询 | AI 正常答 | 记录 |
| 投诉/索赔/平台介入 | AI 只发安抚 + "我帮您核实，稍后给您答复" | **立刻告警**，进「待接管」队列，人可随时接手 |
| 连续 2 轮没解决 | AI 继续安抚 | 升级告警 |

这样对外仍然是「全自动、无转人工」，对内保留了一条人命线。**商业化产品必须有这条线，否则一次批量答错就是赔偿 + 差评 + 封店。**

## 七、成本：你担心的「几千个上下文」其实不成立

### 7.1 先纠正一个误解

**订单上下文不是「每个用户存一份」**。它是**按需检索、用完即弃**的：

- 会话记忆：只保留最近 8–10 条消息（几百 token）；
- 订单信息：只有问到物流/售后时才查一次，拼进当次请求；
- 知识：按问题检索 3–5 条，不整库塞进去。

所以「几千个用户」不会产生「几千份存储」，存储成本约等于 0。

### 7.2 真实成本估算（按条计）

单条请求大致：系统提示 400 + 知识 600 + 会话 300 + 订单 150 ≈ **1450 input tokens**，输出 **120 tokens**。

| 模型档位 | 单价（输入/输出，每百万 token） | 单条成本 | 1000 条/天 | 1 万条/天 |
|---|---|---|---|---|
| 国产中档（DeepSeek 级） | ¥2 / ¥8 | ≈ ¥0.004 | ¥4/天 | ¥40/天 |
| 国产高档 | ¥15 / ¥60 | ≈ ¥0.029 | ¥29/天 | ¥290/天 |

> 价格为公开牌价的量级估算，实际以账单为准；命中缓存还能再降。

**结论**：一条自动回复的模型成本是「几厘钱」。1000 条/天一个月一百多块。对比一个客服 ¥5000–8000/月，成本不构成约束。

**真正贵的是「答错」**：一次纠纷赔偿 + 一个差评 + 回复率掉档，随便一项都超过一年的 token 费。

所以钱应该花在：**知识库质量、评测集、熔断机制**，而不是省 token。

## 八、分期建议

| 版本 | 内容 | 目的 |
|---|---|---|
| v0.1（已完成） | 桌面客户端 + 本地服务 + 知识库 | 验证回复引擎 |
| **v0.2** | Electron 壳：多店分区、店铺列表、内嵌切换、preload 注入 | **验证指纹与登录态**（决定生死） |
| v0.3 | 巡场引擎 + 熔断 + 静默接管 | 全自动跑通一个店 |
| v0.4 | 多店并行 + 汇总看板 | 一个人守多店 |
| v1.0 | 一键评论、激活码、自动更新、签名公证 | 可卖 |
| v2.0 | 服务市场 / 官方 API | 规模 |

**v0.2 的第一件事不是写代码，是「体检」**：新壳登录一个店，人工用三天，看弹几次验证。这个结果决定要不要继续投 Electron。
