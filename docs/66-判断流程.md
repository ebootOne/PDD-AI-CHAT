# 判断流程（Agent 默认工作方式）

> 目的：不靠“你要有判断”的口号，而让不判断就难以前进。

## 一、适用范围

以下变更必须先走判断门：

- 架构、决策权、事实选择方式；
- 产品范围、规则、自动发送/3 分钟策略；
- 成本、计费、模型调用方式；
- 合规、隐私、权限；
- 用户说“开始/继续/重构”，但方案还没有判断记录。

普通拼写、低风险小修可直接改，但仍要自审。

## 二、判断门

第一轮**只判断，不改代码**。判断记录至少包含：

1. **结论**：对 / 部分对 / 不对；
2. **前提**：什么条件下成立；
3. **反例**：什么场景会失败；
4. **最高原则影响**：P0-1 回复率、P0-2 准确率、P0-3 真实解决；
5. **成本/延迟/范围影响**；
6. **建议**：做 / 改 / 不做。

用户说“开始”时，如果没有判断记录，先补判断，不直接实现。

## 二点五、个例还是类问题

修复前先判断影响面，避免两种错误：

- 把类问题当单例，继续打补丁；
- 把单例强行抽象，过度设计。

判断问题：

1. 换一个实体/属性/商品/渠道，同样机制还会不会错？
2. 是数据缺失、平台一次性变化，还是判断能力缺失？
3. 影响的是关键事实，还是边角表达？

- **类问题**：抽象到可复用层，并用至少一个跨实体/跨场景变体验证；验证不过，说明抽象不够。
- **确属单例**：记录边界、理由、不再扩散的条件，不强行抽象。
- **高风险且不确定**：先按类问题处理，直到证明是单例。

## 三、反方评审

判断记录完成后，交给独立上下文的反方 agent：

- 只允许找反例、找违背最高原则、找成本/范围风险；
- 不允许写代码、不允许给实现方案；
- 输出：成立 / 有保留 / 不成立，以及证据。

反方不是走过场；如果找不到反例，要说明边界，而不是默认通过。

## 四、验收先行

写代码前先定：

- 成功标准；
- 致命错误标准（错单/错价/编造/越权/超时）；
- 验证用例（真实/回放/故障注入）；
- 不通过怎么回滚。

没有验收标准，不进入实现。

## 五、决策日志

每个架构/规则决定记录到 `docs/decisions/`：

- 当时的前提；
- 被否掉的方案；
- 为什么选这个；
- 后来是否被证伪；
- 关联提交/测试。

新会话先读相关决策日志，不靠记忆。

## 六、流程

```
方案
  → 判断记录（不改代码）
  → 反方评审
  → 验收标准
  → 用户确认
  → 实现
  → 验证
  → 更新决策日志
```

## 七、诚实边界

这套流程能减少附和式执行，但不能保证我永远判断正确。  
如果判断记录、反方意见、验收标准缺失，用户可以直接拒绝进入实现。
