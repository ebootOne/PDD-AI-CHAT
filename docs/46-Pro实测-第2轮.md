## 三、问题 1：测试会不会触发注册表更新

**会，但只覆盖「wide / empty」这一类。**

- 25 问里 11 条新说法进了 `data/route-gaps.json`：
  一根能用多久、发错货了怎么办、你们几点上班、能给仓鼠磨牙吗、有赠品吗、抽纸能擦嘴吗、站杆会不会发霉、买两个能便宜点吗、今天下单明天能到吗、包装结实吗、抽纸多少抽；
- 只有 1 条命中既有注册表（「公司抬头能开票吗」→ 发票）；
- 对缺口点「让模型提议」可用：`一根能用多久` → `usage / manual / 0.85`，说明“使用寿命属于说明书”，可直接采纳。

**机制缺口（ISS-028）**：本地 `mode=normal` 答的题不进缺口。
比如「种子几天发芽」被本地判成到货时效、答了物流天数，但因为它没走 wide，**不会出现在缺口里**。
——测试能发现错误，注册表却收不到，闭环漏了一半。

## 六、建议

1. **修 ask 误判（P1）**：`发芽/出苗/开花` 语境下，「几天」不能归 arrival_time；
2. **本地答错也记缺口（P2）**：judge 判 fallback / 维度错时，写 `route-gaps`，别只靠 wide；
3. **售后类兜底给出口（P2）**：没有 ask 时按关键词/意图兜到 `after_sale` 口径；
4. **单位/维度校验（P2）**：问「抽」答「张」要被 judge 拦（同 ISS-024 的“限定词”问题）；
5. **offtopic 判定已修**：有商品上下文时不再说「帮不上忙」。

## 八、ISS-025 修复（2026-11-09）

根因：`arrival_time` 规则含裸「几天」，且顺序在 `usage` 之前——「种子几天发芽」先撞时长词，`发芽` 没参与判断。

修法（对象优先，不是加关键词）：

1. 到货时效必须带「到/收到/发货后/物流」；「种子几天发芽/催芽要几天/泡几天」归 usage；「几天发货」归 shipping_time；
2. 本地候选缺所问数值（judge.missingDims）→ 升级模型，不再直接兜底；
3. 后端 prompt：事实里有数字必须写出来。

结果：pro / standard 均答「温水浸种4~6小时…一般3~5天露白」。单测 77/77，双引擎 39/39。
